# Frontend: план двух разработчиков на 5 часов

Общая цель, правила продукта и сценарий демонстрации описаны в [MVP_PLAN.md](MVP_PLAN.md). Раздел 11 этого файла — общий контракт с backend. Frontend отвечает за работающий путь бизнеса и команды в браузере, вызовы API, визуальное объяснение рейтинга и сквозную проверку.

## Зона ответственности

- `web/` и `web/Dockerfile`: React + TypeScript + Vite, CSS, маршруты/экраны, формы, клиент API и прокси `/api` на `api:8000` в Compose.
- `e2e/`: один Playwright сценарий полного пользовательского пути для сервиса `e2e` в Compose профиле `test`.
- Пользовательские разделы README: экраны, демо-акторы, сквозной сценарий, запуск Playwright. Финальную правку README согласовать с backend, чтобы команды не редактировали его одновременно.
- Отображение и обработка состояний запроса: загрузка, ошибки, пустые списки, сохранение после обновления страницы, источник вопросов `llm`/`fallback`.

## Разделение работы без пересечения файлов

| Разработчик | Что делает | Файлы, которые редактирует только он |
| --- | --- | --- |
| **Фронт 1 — конструктор задачи** | Кабинет бизнеса (`mine`), создание черновика, 3–5 вопросов и ответы, полная редактируемая карточка, `score-preview`, расшифровка рейтинга, ручное подтверждение/публикация, повторное редактирование опубликованной задачи. После основного сценария — сквозной Playwright. | `web/src/features/business/**`, `e2e/**` |
| **Фронт 2 — каталог и решения** | Создаёт Vite-проект, общие типы и транспорт API, демо-переключатель, маршруты и общий CSS. Делает каталог, фильтры, публичную карточку, отклик команды, список и статусы предложений у бизнеса, подтверждение прогресса, баллы команды. | `web/package.json`, `web/index.html`, `web/vite.config.ts`, `web/tsconfig*.json`, `web/Dockerfile`, `web/src/main.tsx`, `web/src/App.tsx`, `web/src/shared/**`, `web/src/features/catalog/**`, `web/src/features/proposals/**`, `web/src/styles.css` |

Если нужны локальные стили, каждый держит их рядом со своим компонентом. Глобальные стили и навигацию меняет только фронт 2. `compose.yaml`, `.env.example` и корневой `README.md` редактирует backend; фронт 2 передаёт ему готовый текст о пользовательском сценарии и запуске Playwright. Общий контракт API меняется только после согласования всех троих в разделе 11 [MVP_PLAN.md](MVP_PLAN.md).

**Стык между двумя частями:** фронт 2 до 30-й минуты создаёт `web/src/shared/types.ts` с `Task`, `CardFields`, `Rating`, `Question`, `Proposal`, `Team` и `web/src/shared/api.ts` с единым `request<T>(path, { method, body, actorId })`. Функция обращается к относительному `/api/...`, ставит `X-Demo-Actor-Id` для действий актёра и превращает `detail` ошибки в читаемый текст. Фронт 1 использует эти файлы, но не редактирует их; вызовы своих endpoint держит в `features/business/api.ts`. Фронт 2 держит вызовы каталога и предложений в своих feature-модулях. Сервер остаётся единственным источником рейтинга и порядка каталога.

**Стык экранов:** фронт 1 экспортирует из `features/business` компоненты `BusinessWorkspace({ businessId })` и `TaskEditor({ businessId, taskId?, onPublished })`; `onPublished(taskId)` вызывается только после успешного `confirm`. Фронт 2 подключает их в `App.tsx`: `/business` — кабинет, `/business/tasks/new` и `/business/tasks/:id/edit` — редактор, `/tasks/:id` — карточка и отклики. Для открытия опубликованной задачи кабинет использует обычную ссылку `/tasks/:id`; редактор после публикации передаёт ID в `onPublished`, а `App.tsx` открывает ту же страницу. Фронт 1 не меняет маршруты, фронт 2 не редактирует форму и рейтинг.

Разработчики работают в отдельных ветках и объединяют изменения через обычный merge. Перед объединением каждый коммитит только свою зону файлов; временные fixtures лежат внутри соответствующей feature и повторяют JSON из раздела 11. Это позволяет начать экраны до готовности backend и убрать fixtures без переписывания UI.

## Очерёдность работы

| Время | Фронт 1 — конструктор | Фронт 2 — каталог и решения | Контрольная точка |
| --- | --- | --- | --- |
| 0–30 мин | Согласовать поля и интерфейс двух экспортируемых компонентов; создать папку feature и макет формы по `CardFields`. | Согласовать с backend раздел 11, создать Vite, типы, `request`, `App.tsx`, демо-переключатель и маршруты. | К 30-й минуте фронт 1 импортирует общие типы; оба знают точные поля JSON и роли. |
| 30–100 мин | Кабинет `mine`, новый черновик, вопросы, перенос ответов и редактируемая карточка; временный fixture при необходимости. | Каталог, фильтры и публичная карточка; использовать порядок API, показывать задачи с баллом ниже 40. | Черновик открывается в редакторе; каталог виден всем командам. |
| 100–165 мин | `score-preview`, разбивка и подсказки; подтверждение, публикация и редактирование; ошибки без потери текста. | Форма отклика команды, её сохранённые предложения после refresh; показ баллов из `/api/teams`. | В `App.tsx` подключены реальные экспорты фронта 1, опубликованная задача открывается по `/tasks/:id`. |
| 165–225 мин | Подключить живые endpoint конструктора, убрать его fixtures из рабочего режима; подготовить Playwright для пути создания и публикации. | Список всех откликов у бизнеса, ручной выбор/отклонение, подтверждение прогресса и отображение начисленных баллов; подключить живые endpoint. | Полный путь работает вручную; несколько команд выбираются независимо, повторное подтверждение прогресса недоступно. |
| 225–270 мин | Дополнить Playwright откликом, решением и refresh; проверить fallback AI и ошибки формы. | Исправить интеграционные проблемы своих экранов, проверить фильтры и задачу ниже 40, передать backend текст для README. | Вместе с backend пройти один сквозной сценарий на реальном API. |
| 270–300 мин | Проверить узкий экран редактора и репетировать ввод слабого описания. | Проверить узкие экраны каталога и карточки, помочь с README и репетицией. | Другой участник проходит демо до 5 минут без подсказок. |

## Экраны и поведение

1. **Переключатель демо-актора.** Получать бизнесы и команды из `/api/demo-actors`; не прошивать ID. Показывать текущую роль и имя. При смене роли обновлять доступные действия. Все действия бизнеса/команды отправляют `X-Demo-Actor-Id` выбранного актёра.
2. **Кабинет бизнеса.** Показывать собственные `draft` и `published` из `/api/tasks/mine`. Создавать черновик из описания и темы. Получать 3–5 вопросов, показывать `source` и переносить ответы в соответствующие редактируемые поля. Дать редактировать все поля `CardFields`; кнопка подтверждения явно публикует или обновляет карточку. При ошибке сохранить введённое в форме и показать `detail`.
3. **Рейтинг.** Запрашивать `score-preview` для текущей формы, показывать число, уровень, начисленные пункты и конкретные `missing.hint`. Подписать предварительный результат как предварительный. После `confirm` показывать сохранённый рейтинг из ответа API. Не рассчитывать рейтинг по отдельной клиентской формуле.
4. **Каталог.** Запрашивать `/api/tasks` с темой/уровнем и использовать порядок сервера. Показывать все опубликованные задачи, включая 0–39. Открывать карточку с подтверждёнными полями и рейтингом. Предусмотреть пустое состояние фильтра; не блокировать отклик из-за низкого балла.
5. **Путь команды.** На карточке отправлять идею, план, срок и HTTP(S)-ссылку. Показывать серверные ошибки; после успеха показывать сохранённое предложение и после refresh получать его из `/api/tasks/:id/my-proposals`. Баллы команды показывать из `/api/teams`, обновлять после подтверждения прогресса бизнесом.
6. **Путь бизнеса после отклика.** Показывать все предложения своей задачи и статус каждого. Кнопки «Выбрать»/«Отклонить» отправляют явный `PATCH`; поддержать несколько выбранных и отсутствие выбора. Для выбранной команды дать подтверждение короткого описания прогресса; после успеха показать начисленные 10 баллов. Загружать `/api/tasks/:id/progress` и не предлагать повторное подтверждение уже учтённой пары.

## Работа параллельно с backend

Фронт 2 сразу создаёт общие типы и транспорт по разделу 11; фронт 1 подключает их по фиксированным путям. Временные fixtures должны возвращать те же структуры, включая `draft`, `published`, `fallback`, ошибки и низкий рейтинг. Feature-модули вызывают общую функцию `request`, поэтому подключение живых endpoint не требует переписывания форм. Не добавлять собственные поля, обёртки массивов или правила рейтинга; если контракту не хватает данных, согласовать правку в общем плане.

## Проверки своей команды

- Playwright: слабое описание → минимум три вопроса → ответы и рост preview → подтверждение → каталог → отклик команды → выбор бизнесом → подтверждение прогресса → проверка баллов после refresh.
- Ручная проверка: опубликованная задача ниже 40 видна в каталоге и принимает отклик; фильтры работают; второй отклик можно отклонить независимо от первого.
- Ручная проверка: неверный URL и пустой план показывают ошибки без потери текста; недоступный AI показывает `fallback`; несохранённые изменения опубликованной карточки не появляются в каталоге.
- Проверить ключевые экраны на узкой ширине, видимые подписи полей и читаемые сообщения об ошибках.
