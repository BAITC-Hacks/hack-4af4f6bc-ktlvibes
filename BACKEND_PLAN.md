# Backend: план команды на 5 часов

Общая цель, формула рейтинга и сценарий демонстрации описаны в [MVP_PLAN.md](MVP_PLAN.md). Контракт JSON и маршрутов зафиксирован в разделе 11 этого файла. Backend отвечает за серверную логику, данные, API и запуск всех сервисов через Compose. Frontend может работать параллельно по этому контракту.

## Зона ответственности

- `api/app/`, `api/tests/`, `api/seed.py`, `api/Dockerfile`: FastAPI, Pydantic/SQLModel, AI-адаптер и fallback, рейтинг, маршруты и тесты.
- `db/init/`, `compose.yaml`, `.env.example`: PostgreSQL, отдельная тестовая БД, том, ожидание готовности, окружение и запуск. В Compose предусмотреть сервисы `db`, `api`, `web` и профиль `test` для `e2e`; `web/Dockerfile` и `e2e/` поставляет frontend.
- Разделы README про архитектуру API, переменные окружения, запуск, seed, pytest, формулу рейтинга и AI; согласовать финальную правку README с frontend, чтобы команды не редактировали его одновременно.
- Серверные проверки владения задачей и откликом, валидация, сохранение и начисление баллов. Демонстрационный заголовок `X-Demo-Actor-Id` не считать настоящей авторизацией.

## Очерёдность работы

| Время | Backend | Проверяемый результат |
| --- | --- | --- |
| 0–30 мин | Вместе с frontend зафиксировать раздел 11 общего плана. Поднять FastAPI, `/api/health`, PostgreSQL 17, модели, Dockerfile и Compose с прокси-адресом `api:8000`. | API отвечает; БД готова; frontend знает точные имена полей и формы ответов. |
| 30–100 мин | Создать таблицы и идемпотентный seed. Реализовать демо-акторов, создание/список черновиков, вопросы через LLM или шаблонный fallback, подтверждение и публикацию карточки. | Черновик сохраняется; возвращаются 3–5 вопросов; опубликованная карточка переживает перезапуск. |
| 100–165 мин | Сделать чистую `scoreTask`, уровни, разбивку, подсказки, `score-preview` и атомарный пересчёт на `confirm`. | Пустая/полная карточки дают 0/100; смена подтверждённых полей меняет балл; публичная версия не меняется при ошибке подтверждения. |
| 165–225 мин | Добавить каталог, сортировку/фильтры, карточку, команды, отклики, ручной выбор/отклонение и подтверждение прогресса. | Команда видит любой `published`, в том числе ниже 40; несколько откликов сохраняются; выбранная команда получает 10 баллов один раз. |
| 225–270 мин | Пройти контракт с frontend на реальном API. Закрыть ошибки состояния, AI-сбои и проверки доступа; запустить pytest на `aisana_test`. | API-тесты проходят без изменения демо-БД; полный путь работает через браузер. |
| 270–300 мин | Записать серверные команды в README, проверить чистый `docker compose up --build`, seed и сохранность тома после `down`/`up`; помочь с репетицией. | Другой участник поднимает сервисы одной командой. |

## Реализация и условия приёмки

1. **Данные и запуск.** Создать все поля сущностей из раздела 3 общего плана. `db` имеет healthcheck; API ждёт БД, создаёт схему и выполняет идемпотентный seed. `db/init/` создаёт `aisana_test`; pytest использует только её. Порт БД наружу не нужен. Seed включает минимум 5 черновиков, 5 опубликованных карточек разных уровней (одна ниже 40), 5 команд и 5 откликов. Повторный запуск не создаёт дубликаты.
2. **Контракт.** Реализовать маршруты и формы JSON из раздела 11. Ответы используют `camelCase`, а ошибки дают понятный `detail`. Быстро согласовывать любое изменение контракта с frontend в общем плане до изменения кода. Добавить `/api/demo-actors` и `/api/tasks/mine`, чтобы переключатель и кабинет не зависели от прошитых ID.
3. **Карточки.** Бизнес может видеть только свои черновики. При `confirm` проверять `title` и `topic`, сохранять всю карточку, `confirmedAt` и рейтинг в одной транзакции. Для изменения опубликованной задачи принимать полный новый вариант и заменять публичную версию только после успешного подтверждения. `score-preview` ничего не записывает.
4. **Рейтинг.** Реализовать одну функцию `scoreTask(confirmedCard)` с весами из раздела 4. Не начислять баллы за пустые строки и заглушки. Уровень вычислять отдельно по границам 39/40, 69/70, 89/90. Возвращать для каждого пункта разбивку и конкретную подсказку, когда балл не начислен. Каталог сортировать по `score DESC`, затем `confirmedAt DESC`; фильтровать только `published` по теме и уровню.
5. **AI.** Отправлять LLM только исходное описание и заполненные поля. Проверять формат ответа Pydantic-моделью: 3–5 вопросов, разрешённые `field`, ограничение длины. При отсутствии ключа, тайм-ауте, ошибке сети или неверном JSON отдавать шаблонные вопросы с `source: "fallback"`. AI не заполняет поля и не публикует задачу.
6. **Отклики и баллы.** Отклик принимает непустые идею, план и срок, HTTP(S)-ссылку на прототип и ID команды из заголовка. `my-proposals` возвращает только отклики этой команды; бизнес получает все отклики своей задачи. Владелец задачи явно выбирает или отклоняет каждый отклик; можно выбрать несколько или ни одного. Прогресс подтверждается только для выбранной команды, а `GET progress` возвращает уже подтверждённые пары. Уникальность пары `taskId`/`teamId` в подтверждениях защищает от повторного начисления; вставка подтверждения и `points += 10` выполняются атомарно.

## Проверки своей команды

- pytest: 0/100, все весовые категории, заглушки и границы уровней.
- API: повторное подтверждение/ошибка не меняют опубликованную версию; рейтинг ниже 40 не скрывает задачу; сортировка и фильтры корректны.
- API: чужой бизнес не редактирует задачу; отклик привязан к команде из заголовка, а `my-proposals` не раскрывает чужие отклики; неверный URL, пустой план и несуществующий ID отклоняются.
- API: fallback при неверном JSON/тайм-ауте; прогресс только выбранной команде и только один раз; демонстрационные данные остаются нетронутыми после pytest.

## Передача frontend

К 30-й минуте предоставить контракт из раздела 11, названия демо-бизнеса и демо-команды, базовый URL `/api`, а также примеры успешного `Task`, `rating`, `Proposal` и ошибки. После каждого готового этапа дать frontend работающий endpoint и указать, какой сценарий уже можно подключать. Зафиксировать любые уточнения в общем плане до интеграции.
