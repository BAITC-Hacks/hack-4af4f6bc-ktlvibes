# План разработки и проверки MVP AI Sana (5 часов)

Для параллельной работы двух команд: [план backend](BACKEND_PLAN.md) и [план frontend](FRONTEND_PLAN.md). Этот файл остаётся общим описанием продукта; раздел 11 фиксирует контракт между командами. При изменении контракта обе команды обновляют его здесь до изменения реализации.

## 1. Цель и границы

За 5 часов получить запускаемое веб-приложение со сквозным сценарием: бизнес вводит слабое описание → получает минимум три уточняющих вопроса → редактирует и подтверждает карточку → видит объяснимый рейтинг → публикует задачу → команда находит её в общем каталоге и отправляет предложение → бизнес вручную выбирает или отклоняет предложение → после подтверждения прогресса выбранной команде начисляются баллы.

**Критерий готовности:** весь сценарий проходит в браузере с сохранением данных после обновления страницы. Слайды и заранее прошитые переходы не заменяют работающие действия.

Разграничить два состояния: `draft` (ещё не опубликован и доступен только в кабинете бизнеса) и `published` (виден всем командам при любом рейтинге, включая 0–39). Публикация требует явного подтверждения бизнесом. Редактирование опубликованной задачи тоже требует подтверждения; до него в каталоге остаётся последняя подтверждённая версия и её рейтинг.

В MVP нет регистрации, чата, файлов, производственной инфраструктуры и автоматического назначения команд. Для демонстрации используется переключатель тестовых пользователей «Бизнес / Команда». Это не механизм защиты учётных записей.

## 2. Рекомендуемый стек и архитектура

| Слой | Решение | Причина для 5-часового MVP |
| --- | --- | --- |
| Интерфейс | React + TypeScript + Vite, обычный CSS | Быстрый старт и небольшое число экранов. |
| API | Python 3.12 + FastAPI + Uvicorn | Быстрые маршруты, встроенная проверка запросов через Pydantic и OpenAPI. |
| Хранилище | PostgreSQL 17 + SQLModel + psycopg | Общая реляционная БД для каталога, откликов и транзакций. |
| Контракты | Pydantic-модели FastAPI; TypeScript-типы клиента по зафиксированному JSON-контракту | Проверка входных данных и ответа AI на сервере. |
| Тесты | pytest + FastAPI TestClient для логики/API; один Playwright E2E на Chromium | Проверка формулы, переходов состояний и полного пользовательского пути. |
| AI | Серверный адаптер к уже доступному команде LLM API + локальный детерминированный fallback | Демонстрация работает и при отсутствии ключа или сети. |

Структура: `web/` (Vite, React, TypeScript), `api/app/` (FastAPI, модели, БД, рейтинг, AI), `api/tests/`, `api/seed.py`, `e2e/`, `compose.yaml`, `web/Dockerfile`, `api/Dockerfile`, `.env.example`. На клиенте все вызовы идут по относительному пути `/api`; Vite проксирует его в контейнер `api`. Ключ AI хранится только в окружении API.

`docker compose up --build` запускает три сервиса: `db`, `api`, `web`. База использует официальный образ `postgres:17-alpine` и именованный том `postgres_data`, чтобы данные переживали перезапуск контейнеров. `db` имеет healthcheck; `api` ждёт готовности БД, создаёт схему через `SQLModel.metadata.create_all` и выполняет идемпотентный seed при первом запуске; `web` открывается на `http://localhost:5173`. Внутри сети Compose API подключается к `db:5432`, а web — к `api:8000`. Порт БД наружу для демонстрации не нужен. `docker compose down` останавливает сервисы и сохраняет том. `docker compose down -v` использовать только для намеренного сброса демо-данных.

В `db/init/` положить SQL-скрипт создания отдельной базы `aisana_test`. Тесты: `docker compose exec api pytest -q`; Playwright запускается командой `docker compose --profile test run --rm e2e` против работающего web-сервиса. API-тесты подключаются только к `aisana_test` и не меняют демонстрационные данные. Контейнер `e2e` запускается по требованию и не участвует в обычном `up`. Конкретные команды запуска и URL записать в README. Предусловие: установлен и запущен Docker Desktop с Compose.

## 3. Данные и правила состояний

| Сущность | Минимальные поля |
| --- | --- |
| `businesses` | `id`, `name` (синтетические демо-пользователи) |
| `tasks` | `id`, `businessId`, `status`, `initialDescription`, `topic`, `title`, `context`, `need`, `users`, `dataDescription`, `dataAccess`, `constraints`, `expectedResult`, `successMetric`, `successTarget`, `contact`, `interactionFormat`, `score`, `confirmedAt`, `createdAt`, `updatedAt` |
| `teams` | `id`, `name`, `interests`, `skills`, `technologies`, `points` |
| `proposals` | `id`, `taskId`, `teamId`, `idea`, `plan`, `duration`, `prototypeUrl`, `status` (`submitted`, `selected`, `rejected`), `createdAt` |
| `progressConfirmations` | `id`, `taskId`, `teamId`, `note`, `points`, `confirmedAt` |

Все поля карточки существуют в схеме, даже если значение пустое. Не хранить рейтинг как произвольный ввод: сервер пересчитывает и сохраняет его в одной транзакции с подтверждением карточки. `score` у неподтверждённого черновика не публикуется; на форме допустимо показывать «предварительный рейтинг».

`businessId` и `teamId` выбираются в демо-переключателе и передаются заголовком `X-Demo-Actor-Id`. Сервер проверяет, что редактирование и решение относятся к выбранному `businessId`, а отклик — к выбранному `teamId`. Без настоящей аутентификации эти ID можно подменить; это осознанное ограничение демо-версии.

## 4. Рейтинг и каталог

Единая чистая функция `scoreTask(confirmedCard)` возвращает `{ total, level, breakdown, missing }`. Она используется сервером и тестами; клиент получает результат API. Начислять баллы только за подтверждённые, непустые значения, прошедшие простую проверку формата и отсеивание заглушек вроде «позже»/«не знаю». Для текстовых полей задать понятный минимальный объём, например 12 содержательных символов. Рейтинг измеряет **полноту описания**, а не доказанную правдивость бизнес-данных.

| Условие | Баллы |
| --- | ---: |
| Контекст описан | 10 |
| Потребность/изменение описаны | 10 |
| Описаны доступные данные или примеры | 10 |
| Указан источник и способ доступа к ним | 10 |
| Конкретный ожидаемый результат | 15 |
| Критерий успеха: метрика или проверяемое условие | 10 |
| Критерий успеха: целевое значение/условие принятия | 5 |
| Ограничения или явное указание их отсутствия | 10 |
| Целевые пользователи | 10 |
| Валидный контакт | 5 |
| Формат консультаций и обратной связи | 5 |
| **Итого** | **100** |

Уровни: 0–39 «черновик», 40–69 «рабочая», 70–89 «готовая», 90–100 «приоритетная». Название уровня «черновик» не равно техническому статусу `draft`: опубликованная задача с 30 баллами видна в каталоге. Не повышать рейтинг за фразу «данных нет» в поле доступных данных; честно показать её в карточке и подсказать, что нужны данные/источники. Для каждого неначисленного пункта показать конкретную подсказку. После подтверждённого изменения сортировка каталога обновляется.

Каталог отдаёт **все** задачи со статусом `published`, сортирует по `score DESC`, затем `confirmedAt DESC`; фильтры — тема и уровень готовности. Любая команда может открыть карточку и откликнуться при любом рейтинге. Рекомендательная лента не входит в обязательный путь MVP.

## 5. AI-функция: уточняющие вопросы

Endpoint получает исходное описание и уже заполненные поля. LLM возвращает только список из 3–5 вопросов, привязанных к полям карточки. Пример контракта:

```json
{
  "input": {
    "initialDescription": "Клиенты долго ждут ответ поддержки",
    "card": { "context": "", "need": "", "users": "" }
  },
  "output": {
    "questions": [
      { "field": "users", "text": "Какие группы клиентов сталкиваются с ожиданием?" },
      { "field": "dataDescription", "text": "Какие данные об обращениях доступны команде?" },
      { "field": "successMetric", "text": "По какому показателю вы оцените сокращение ожидания?" }
    ]
  }
}
```

Системный промпт: «Определи недостающие или неясные сведения в описании бизнес-задачи. Верни только JSON по заданной схеме с 3–5 короткими вопросами на русском, каждый с `field` из разрешённого списка. Не утверждай факты о компании, клиентах, данных или сроках, которых нет во входе. Если поля заполнены, спроси о конкретике или способе проверки». Версию промпта и пример входа/выхода положить в README.

Сервер ограничивает время запроса через HTTPX, проверяет JSON Pydantic-моделью, разрешённые `field`, число вопросов и длину текста. При тайм-ауте, ошибке сети или неверном ответе выбирает 3–5 уместных вопросов из шаблонов по незаполненным полям. Ответы пользователя переносятся в редактируемые поля карточки; AI ничего не публикует и не начисляет баллы. На экране указывать, использован ли LLM или fallback, чтобы демонстрация не выдавала заглушку за онлайн-модель.

## 6. Экраны и API

| Экран | Работающее действие |
| --- | --- |
| Бизнес: новый черновик | Ввод короткого текста и темы, сохранение черновика. |
| Бизнес: вопросы и карточка | Минимум 3 вопроса, ответы, редактирование всех полей карточки, предварительный рейтинг, подтверждение и публикация. |
| Каталог | Общий список, рейтинг/уровень, сортировка, фильтры, открытие карточки. |
| Команда: карточка | Отправка идеи, плана, срока и валидной HTTP(S)-ссылки на прототип; сохранённый отклик виден после обновления страницы. |
| Бизнес: предложения | Все отклики к своей задаче, ручные действия «Выбрать» и «Отклонить». Можно выбрать несколько или не выбрать никого. |
| Бизнес: результат | Для выбранной команды подтверждение короткого описания прогресса; один раз начислить 10 баллов этой команде. |

Минимальный API:

```text
POST   /api/tasks/drafts             создать черновик
POST   /api/tasks/:id/questions       получить вопросы
PUT    /api/tasks/:id/confirm         сохранить подтверждённую карточку, пересчитать рейтинг, опубликовать
GET    /api/tasks?topic=&level=       каталог, порядок задаёт сервер
GET    /api/tasks/:id                карточка
POST   /api/tasks/:id/proposals       отправить отклик
GET    /api/tasks/:id/proposals       список откликов для бизнеса
PATCH  /api/proposals/:id/status      выбрать или отклонить вручную
POST   /api/tasks/:id/progress        подтвердить прогресс выбранной команды
GET    /api/teams                     список команд
POST   /api/teams                     добавить команду без регистрации
```

Валидация на сервере: обязательные `title` и `topic` при публикации; корректный URL прототипа; непустые идея, план и срок; существующие ID; запрет прогресса для невыбранной команды; повторное подтверждение того же прогресса не начисляет очки. Возвращать понятные ошибки `400`, `404`, `409`; ошибку AI перехватывать fallback. Число откликов на задачу не ограничивать.

## 8. Тестовые данные и проверка

`api/seed.py` создаёт не менее 5 разнополных черновиков, 5 опубликованных карточек с полями и рассчитанным рейтингом (включая одну ниже 40), 5 профилей команд и 5 откликов. Seed идемпотентен: повторный старт контейнера не создаёт дубликаты. В README назвать демо-бизнес и демо-команду.

**Автотесты, которые защищают ключевую механику:**

1. `scoreTask`: пустая карточка = 0, полностью заполненная = 100, проверка каждой весовой категории, заглушки не дают баллов. Отдельно `getLevel`: границы 39/40, 69/70, 89/90 (сама формула начисляет баллы с шагом 5).
2. API: подтверждение сохраняет карточку и пересчитывает рейтинг; неподтверждённые изменения не меняют опубликованную карточку; задача с рейтингом ниже 40 остаётся в каталоге и принимает отклики.
3. API: каталог сортируется по баллу и фильтруется по теме/уровню; несколько разных команд откликаются; выбор/отклонение происходит только по явному запросу бизнеса.
4. API: AI возвращает минимум 3 вопроса; некорректный JSON/тайм-аут включают fallback; AI не заполняет факты в карточке.
5. API: баллы за прогресс получает только выбранная команда, только после подтверждения, один раз; сохранение решения и начисление баллов атомарно в PostgreSQL.
6. Playwright: ввод слабого описания → ответы и рост рейтинга → публикация → поиск в каталоге → отклик команды → ручной выбор бизнесом → подтверждение прогресса. Проверить сохранение после перезагрузки.

**Ручная приёмка перед защитой:** открыть приложение в чистом состоянии; пройти тот же путь; проверить 0–39 в каталоге; сменить фильтры; отправить второй отклик; отклонить один, выбрать другой; отключить AI API и повторить создание; попробовать пустой план и неверный URL; выполнить `docker compose down` и повторный `docker compose up`, убедиться, что данные в именованном томе сохранились.

1. **0:00–1:00:** бизнес вводит «Клиенты долго ждут ответа поддержки». Показать минимум три вопроса.

## 11. Общий контракт backend ↔ frontend

Это минимальная договорённость для параллельной разработки. JSON использует `camelCase`, ID — целые числа, даты — строки ISO 8601 в UTC. Клиент вызывает только относительные пути `/api/...` и передаёт выбранный ID в `X-Demo-Actor-Id` для действий бизнеса или команды. Тип актёра определяется маршрутом; этот заголовок не является аутентификацией. Ошибки валидации и состояния возвращаются с понятным `detail` и кодом `400`, `404` или `409` (FastAPI также может вернуть стандартный `422` для неверной формы JSON). Клиент показывает текст ошибки.

**Поля карточки для `confirm` и `score-preview`:** `topic`, `title`, `context`, `need`, `users`, `dataDescription`, `dataAccess`, `constraints`, `expectedResult`, `successMetric`, `successTarget`, `contact`, `interactionFormat`. Все строковые поля; пустая строка допустима там, где поле не обязательно для публикации. `initialDescription` задаётся при создании черновика и возвращается в `Task`. Серверные поля `id`, `businessId`, `status`, `score`, `confirmedAt`, `createdAt`, `updatedAt` клиент не отправляет как часть карточки. `confirm` принимает полный объект карточки и атомарно заменяет подтверждённую версию; пока запрос не успешен, публичная карточка и рейтинг не меняются. Несохранённые правки живут в форме клиента.

**Ответ `Task`:** все поля из таблицы `tasks` раздела 3 плюс `rating`. У черновика `score`, `confirmedAt` и `rating` равны `null`; у опубликованной задачи `rating = { total, level, breakdown, missing }`, `score = rating.total`. `breakdown` — массив `{ key, earned, max }`; `missing` — массив `{ key, hint }`. Уровень — один из `черновик`, `рабочая`, `готовая`, `приоритетная`. Предварительный рейтинг имеет ту же форму `rating`, но не меняет БД.

| Маршрут | Запрос | Успешный ответ |
| --- | --- | --- |
| `GET /api/health` | Без тела | `{ "status": "ok" }` |
| `GET /api/demo-actors` | Без тела | `{ "businesses": Business[], "teams": Team[] }` для переключателя |
| `POST /api/tasks/drafts` | `{ "initialDescription": string, "topic": string }` + ID бизнеса | `Task` со статусом `draft` |
| `GET /api/tasks/mine` | ID бизнеса | `Task[]` своих черновиков и опубликованных задач |
| `POST /api/tasks/:id/questions` | `{ "initialDescription": string, "card": Partial<CardFields> }` + ID бизнеса | `{ "questions": [{ "field": string, "text": string }], "source": "llm" \| "fallback" }`; 3–5 вопросов |
| `POST /api/tasks/:id/score-preview` | `{ "card": CardFields }` + ID бизнеса | `rating`; без записи в БД |
| `PUT /api/tasks/:id/confirm` | `{ "card": CardFields }` + ID бизнеса | опубликованный `Task` с пересчитанным рейтингом |
| `GET /api/tasks?topic=&level=` | Необязательные фильтры | `Task[]` только опубликованных, порядок сервера |
| `GET /api/tasks/:id` | ID актёра | `Task`; черновик доступен лишь своему бизнесу |
| `POST /api/tasks/:id/proposals` | `{ "idea": string, "plan": string, "duration": string, "prototypeUrl": string }` + ID команды | `Proposal` |
| `GET /api/tasks/:id/my-proposals` | ID команды | `Proposal[]` этой команды для задачи, включая статусы после обновления страницы |
| `GET /api/tasks/:id/proposals` | ID бизнеса-владельца | `Proposal[]` с `teamName` для отображения |
| `PATCH /api/proposals/:id/status` | `{ "status": "selected" \| "rejected" }` + ID бизнеса-владельца | обновлённый `Proposal` |
| `POST /api/tasks/:id/progress` | `{ "teamId": number, "note": string }` + ID бизнеса-владельца | `{ "confirmation": ProgressConfirmation, "team": Team }`; повтор для пары задача/команда — `409`, без новых баллов |
| `GET /api/tasks/:id/progress` | ID бизнеса-владельца | `ProgressConfirmation[]` для отображения уже начисленных баллов |
| `GET /api/teams` | Без тела | `Team[]`, включая `points` |
| `POST /api/teams` | `{ "name": string, "interests": string, "skills": string, "technologies": string }` | `Team` |

`Proposal` содержит поля таблицы `proposals` и `teamName`; `Team` — поля таблицы `teams`; `Business` — `id` и `name`; `ProgressConfirmation` — поля одноимённой таблицы из раздела 3. Для MVP `interests`, `skills`, `technologies` передаются строками. Не вводить разные имена полей или обёртки массивов на разных сторонах без правки этой таблицы.
